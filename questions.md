# Questions and decisions

One row per question in the "Questions" section of [CHALLENGE.md](CHALLENGE.md), each mapped to the decision made and where it lives in the repo. Spec IDs (R, T, C) refer to [SPEC.md](SPEC.md).

| # | Question | Decision | Where |
|---|---|---|---|
| 1 | **Schema modeling.** Store the average, derive it, or both? How are reviewers modeled? | Derived, never stored: `average_rating` is computed from reviews (`with_stats()`). The ACF value is kept only as `legacy_average_rating` for audit. Reviewers are a separate `Reviewer` model, not Django users and not strings on each review. Its pk is `deterministic_uuid('wp_user', id)`, which is also the auth service user id, so the two services link with no runtime call. Only `display_name` is kept. | R1, T3; `app/catalog/models.py`; README "Django schema and migration" |
| 2 | **Postmeta strategy.** What became fields, JSON, or was dropped? | First-class columns: `website_url`, `founded_year`, `headquarters`, `rating`, `reviewer_location`, and the Yoast title and description as `seo_title` and `seo_description`. No JSON field was needed. Dropped: ACF field-reference meta, ACF `reviewer_name` (same as the author's display name in every row), `_wp_page_template`, and WP pages and posts. | R1; README mapping table and "Dropped" list |
| 3 | **Migration approach.** Why this approach, how to re-run safely, and how to scale to 100x? | `manage.py import_wp` is an upsert keyed on the WP id, read-only against MariaDB (`READ ONLY` transaction). It mirrors WP: rows now unpublished, trashed or invalid are deleted. It prints created, updated, unchanged, deleted and skipped counts, and re-running leaves counts identical (tested, including a renamed slug). Scaling to 100x is **not implemented or documented in the repo**. | R2, R10; `app/catalog/wp_import.py`; README "Django schema and migration" |
| 4 | **API contract.** Why this pagination shape, these param names, and what changes for a mobile client? | DRF page-number pagination with the standard `count/next/previous/results` envelope. Params are `industry` (repeatable), `ordering`, `page` and `page_size` (default 20, max 100). Ties break on name then id, so pages never overlap, and the query count is constant per page. Reads are public and JSON-only, with `Cache-Control: public, max-age=30, stale-while-revalidate=120`. Mobile is **not designed for separately**, but nothing in the contract is web-specific. | R6, R7; `app/catalog/api.py`, `test_api.py`; README "Brand listing API" |
| 5 | **Component and state.** Where does `<BrandList />` state live, how is the URL synced, and what is the loading and error UX? | State lives in the URL (`?industry=&ordering=&page=`) and is read on mount and on back/forward. Filter and sort changes use `replaceState` (no history entries), and page changes use `pushState`. Loading: skeleton cards on first load, then the old results stay dimmed with a spinner and no layout jump. Responses are cached per URL for 30s. Errors show a message with Retry, empty results offer Clear filters, and stale responses are ignored. | R22, R23, R24, R25; `frontend/src/BrandList.jsx`, `url.js`, `BrandList.test.jsx` |
| 6 | **SCSS architecture.** Why these partials and tokens, and how does a second engineer add a component? | A 7-1 layout (`abstracts`, `base`, `layout`, `components`, `pages`, plus `main.scss`), compiled with the Sass CLI. Every design token is defined once in `abstracts/_tokens.scss` and emitted as `:root` custom properties. Class names follow the existing WP `theme.css`, not CSS-in-JS or modules. A new component is one partial plus one `@use` in `main.scss`. | R21, T6, T7; `frontend/scss/`; README "SCSS" |
| 7 | **Service boundary.** What does each service own, how is a token validated, what if auth is down, and how do you revoke or change a role? | Auth owns users, password hashes and roles. The main app has no password or role column (checked by a schema query). It verifies RS256 tokens locally against a cached JWKS. With auth down, reads and valid-token edits still work, and a cold cache returns 503. Revocation is by short access-token TTL (10 min) plus refresh tokens stored hashed and revocable (logout or admin action). A role change takes effect on the next refresh. | R8, R9, R11 to R15; C2; `auth/`, `app/config/auth.py`; README "Auth service" and "When the auth service is down" |
| 8 | **Shared library.** What went in and what stayed out, how is it pinned and upgraded, and how do you ship a breaking change without deploying both services at once? | `cauth` holds only JWT verification, the DRF `JWTAuthentication` and `IsEditor` classes, role constants and `deterministic_uuid`. It has no models, views or service logic. It is a versioned wheel that both Dockerfiles install, pinned to an exact version. Breaking claims changes use expand-then-contract: the library accepts claims versions N and N-1, it is deployed to the consumer first, then the issuer changes. Its tests run standalone. | R16 to R20; C4; `libs/`, `libs/README.md`; README "Shared library" |

## Gaps I know about

- Q3 (scaling the migration 100x) and Q4 (mobile clients) are not written up in the repo. The design leaves room for both, but I haven't implemented or documented either.
